# ADR 0018 — Modelo de execução multi-provider

- Status: aceito (2026-10-04)

## Contexto
Até a Wave C, um run executa um único provider. Tarefas híbridas reais cruzam especialistas: "projete um pipeline Spark que produza dados para uma API" precisa do Spark Forge e do API Forge, e o segundo deveria saber o que o primeiro achou. O Forge Protocol já reservava os contratos (`ExecutionPlan`, `VerificationResult`, `WorkspaceDescriptor`, `InstallationPlan`, grafo) e as ops `plan`, `verify` e `estimate`, sem implementação. Coordenar especialistas não pode quebrar as invariantes do core (CLAUDE.md): routing determinístico sem LLM e sem conhecimento de domínio, integração só pelo protocolo, nenhum sucesso sem `ExecutionResult` válido e tudo persistido redigido. Também não pode exigir scheduler, servidor, banco nem processo persistente.

## Decisão
- **Plano local e sequencial.** Uma tarefa vira um `ExecutionPlan` (`theforge/ExecutionPlan/v1`, um DAG de no máximo 8 nós), validado inteiro antes de qualquer execução (todas as violações de uma vez, códigos `FORGE-PLAN-*`) e executado no processo da CLI, um nó por vez, na ordem topológica com desempate por id. Não há concorrência, fila, retomada nem processo persistente.
- **Um run por nó.** Cada nó é um run completo de um único provider pelo mesmo `Forger` do `ask`, com o provider **fixado**: não roteável vira `no_route`, indisponível vira `provider_failure`, e nunca há fallback para outro provider. Todas as garantias das Waves A–C (trust, policy, contexto, integridade, receipt, telemetria) valem para cada nó sem exceção. O run do plano liga os runs de nó pelo `PlanResult` e pelo receipt de `kind = "plan"`.
- **Falha parcial explícita.** Um nó cujo ancestral não tem resultado válido fica `skipped` com `blocked_by` (`FORGE-PLAN-DEPENDENCY-FAILED`); nós independentes continuam. O plano é `ok` só com todos os nós `ok`, `partial` com algum resultado válido, e senão `refused` ou `provider_failure`.
- **Handoff estruturado.** Um nó recebe, em `ExecuteRequest.handoff` (campo aditivo), só itens dos nós declarados em `inputs`: decisão, findings, evidências com o status epistêmico original e referências de artifact com hash, cada item com a origem. Nunca conteúdo de arquivo nem a saída integral. O handoff é redigido, limitado (256 itens, 256 KiB) e truncado de forma determinística; o provider recebe exatamente o que foi gravado. Consumir é opcional: `accepts_handoff` só evita a limitação `handoff-use-undeclared`. A síntese final é determinística e nunca cria findings nem eleva status epistêmico.
- **Decomposição determinística e o limite de `intent-order`.** Sem arquivo de plano, a decomposição lê só os candidatos do routing por sinais: cada provider com pelo menos 2 tipos de sinal qualifica com sua melhor capability, e os qualificados viram um `pipeline` ordenado pela posição, na intenção, da primeira keyword casada de cada um (regra `intent-order`, dependência `inferred` com a regra e a evidência). A ordem textual é um **proxy** do fluxo de dados e pode inferir a dependência errada ("uma API que consome os dados do pipeline Spark" põe a API primeiro). Empates, provider sem keyword casada ou mais qualificados que o perfil permite resultam em `ambiguous`, nunca num chute. `plan --from FILE` é a alternativa explícita: o usuário fixa nós, ordem e dependências, e o arquivo passa pela mesma validação. Só o perfil `max` (até 4 providers) decompõe em vários providers; `economy` e `balanced` usam a decisão de um provider.
- **Ativação de `plan`.** A op `plan` sai de reservada porque tem um uso concreto: antes de executar, o provider pode estimar contexto necessário, classe de operação, artifacts e incógnitas (`PlanRequest`/`PlanEstimate`). Roda com a superfície de `describe`/`health`, só endurece a policy do nó (vale a decisão mais restritiva entre a classe declarada e a estimada) e nunca falha o planejamento (falha vira limitação `FORGE-PLAN-ESTIMATE`).
- **`verify` e `estimate` continuam reservadas.** Não há verificador independente nem uso para uma estimativa de custo nesta versão; o nível `independent` do `VerificationResult` fica sempre `not_performed` e o core nunca envia essas ops.
- **Padrões.** `route` e `pipeline` executam sequencialmente. Desde o ciclo 3 (Wave E), `delegate`, `parallel` e `debate` também executam — os nós independentes de cada nível de dependência em concorrência limitada (`MAX_PARALLEL_NODES` = 4), ordem gravada sempre topológica. `debate` compõe o `DecisionRecord` (artefato `decision`) da evidência `id="decision"` do referee.
- **Workspace, grafo e instalação.** O `WorkspaceDescriptor` descobre repositórios independentes (até 3 níveis, sem seguir symlinks) com a consulta git somente leitura da Wave C, tecnologias com evidência e relações explícitas de `.forge/config/workspace.toml`; nada é inferido. O `WorkspaceGraph` só aceita arestas com evidência. Providers ausentes ou indisponíveis entram em no máximo um `InstallationPlan` por run, somente de planejamento.
- **Compatibilidade.** O protocolo continua `forge/v1`; os campos novos (`RoutingDecision.pattern`, `ExecuteRequest.handoff`, `Capability.accepts_handoff`, `ExecutionInfo.deterministic`, campos do receipt) são aditivos e opcionais, e providers que não os conhecem continuam válidos.

## Alternativas
- **Execução concorrente ou scheduler.** Adiada no ciclo 2 e implementada no ciclo 3 (Wave E) para os padrões com nós independentes: escalonamento por nível de dependência com `ThreadPoolExecutor` limitado, sem fila nem estado compartilhado — cada nó continua um `Forger.ask` isolado. Scheduler/retomada de plano segue fora do escopo.
- **Um único run com vários providers.** Quebraria a garantia "um receipt, um provider, um resultado validado" e o `explain` de cada especialista. Um run por nó reaproveita tudo o que já existe.
- **Passar a saída integral ou arquivos entre nós.** Vazaria conteúdo para providers que não o pediram e incharia o request. O handoff por referência repete a decisão do ContextPack por referência ([ADR 0007](0007-context-pack-by-reference.md)).
- **Ordenar nós por regras de domínio ("dados antes de API").** Coloca conhecimento de domínio no control plane. Ordenar por LLM viola o routing determinístico. A ordem textual é fraca, mas é explicável, determinística e contornável com `--from FILE`.
- **Ativar `verify`/`estimate` junto com `plan`.** Sem caso de uso, seria uma promessa vazia no protocolo que os providers teriam de implementar sem que o core use.

## Consequências
- `theforge plan` coordena especialistas reais sem mudar o `ask`. A prova real rodou em 2026-10-04 com `sparkforge-aws` 0.5.0 e `apiforge` 0.1.0: plano `ok`, o nó de API recebeu os itens de handoff do Spark Forge com o status epistêmico original e `explain` sem divergência. Os adapters reais não declaram `accepts_handoff`, então o nó de API registra `handoff-use-undeclared` ([real-providers.md](../real-providers.md#prova-cross-forge-spark-forge--api-forge)).
- A regra `intent-order` pode errar a direção de uma dependência; a ajuda de `plan` e [cli.md](../cli.md#plan) avisam e recomendam revisar o plano sem `--execute` ou usar `--from FILE`.
- O custo de um plano é a soma dos runs dos nós, mais describe/health por provider distinto, uma op `plan` por nó que a declara e até 20 s de git na descrição do workspace.
